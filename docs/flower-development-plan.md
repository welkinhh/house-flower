# flower · 技术选型与开发计划（历史方案）

> 本文记录的是旧版自定义花束画布方案。2026-09-29 起产品更名为 House花生，功能与页面以当前小程序实现和 docs/local-ai-mock.md 的更新记录为准；本文后续排期与画布设计不再作为当前实施计划。

更新：2026-09-27。状态：历史原型 UI 与本地模拟流程。

## 1. 产品目标与本期交付

flower 是面向个人的花束创作小程序。四个核心入口为花束搭配、照片灵感、花束复刻、场景试花；统一产出可编辑花束方案、花材清单和可保存的花卡。

本期新增基础能力：作品草稿、继续编辑、撤销/重做、云端作品保存与生成任务恢复。正式交易、库存、订单、配送不属于本期范围。采购单位是花店核对参考，不代表真实供应商库存与报价。

现状：E:/Flower 是微信原生 TypeScript 初始项目；现有网页通过 http://127.0.0.1:4173/ 提供。网页功能规则可参考，手机布局、画布交互、花材资产与视觉体系需要重新设计。

## 2. 已定技术方案

| 层次 | 选择 | 理由与边界 |
| --- | --- | --- |
| 小程序 | 微信原生 + TypeScript + WXML + WXSS | 复用当前工程，直接控制 Canvas、图片选择、分享及相册能力；当前目标是微信 |
| 页面渲染 | WebView 渲染 + glass-easel 组件框架 | 第一版降低 Canvas 与组件兼容风险；Skyline 作为后续真机评估项，二者概念不混用 |
| 界面组件 | 自定义轻量组件与设计变量 | 自主实现导航、底部抽屉、花材项、清单、按钮、状态反馈，避免组件库默认样式限制视觉 |
| 花束画布 | Canvas 2D + 花材矢量绘制、透明素材 | 同一份场景数据用于预览和导出；处理命中检测、坐标变换、图层顺序和触摸手势；主流程保持单屏 |
| 状态管理 | 类型化领域对象 + 小型订阅式 store | 画布即时状态留在逻辑层，手势结束再提交场景；页面只接收必要摘要，避免每帧大量 setData |
| 后端 | 腾讯 CloudBase 云函数，TypeScript 编译到平台支持的 Node.js 运行时 | 与小程序身份、存储、数据库及计划资源衔接；不预先绑定未经核实的运行时版本 |
| 数据 | CloudBase 文档数据库 + 本地草稿缓存 | 花束结构与任务适合文档；离线编辑，显式版本号控制云端覆盖 |
| 图片 | CloudBase 云存储 + 缩略图/按需下载缓存 | 主包仅保留首屏必需素材；原图与生成图私有保存，分享文件单独授权 |
| AI | 优先使用计划所属 CloudBase AI 通道；混元能力适配层 | 先确认资源包扣减渠道；不假设普通腾讯云 API、TokenHub 与活动额度通用 |
| 工程与质量 | npm 锁定依赖、TypeScript、ESLint/Prettier、Vitest、微信开发者工具与真机检查 | 重点覆盖 BOM、变换、版本冲突、任务重复提交等业务风险 |

推荐依赖：小程序侧保持轻量；云端 @cloudbase/node-sdk、微信服务端身份上下文 SDK、Zod。具体锁定版本在搭建时与运行时联调。CloudBase 生图当前文档要求 @cloudbase/node-sdk >= 3.18.3、@cloudbase/ai >= 2.30.0；这是接入下限，不把最新版写死为长期选型。

## 3. 腾讯计划与模型接入

用户说明计划提供 100,000 张生图额度，记录为“用户提供、控制台待核实”。目前查到的官方公开成长计划资料存在 10,000 张版本，不能据此认定用户额度错误，也不能把 100,000 张写成已核实权益。以账号实际到账资源包为准，记录总量、剩余量、有效期、环境、模型与扣减通道。

| 产品任务 | 技术路径 | 必须验证的能力 |
| --- | --- | --- |
| 照片灵感 | 本地色彩分析 + 混元视觉理解 + 从花材目录生成结构化建议 | 图片输入、色调和氛围分析；输出经结构校验，目录外花材需映射或提示替代 |
| 花束复刻 | 混元视觉模型识别花材、颜色与可见数量，人工确认后形成 BOM | 遮挡下的估算与未知花材处理；不把隐藏花朵数量当作准确识别 |
| 真实效果图 | 确认的 BOM + Canvas 构图参考图 → 混元图生图 | 参考图输入、品种/配色/构图保留；文生图作为能力受限时的明确替代 |
| 场景融合 | 将透明花束按用户位置合到空间图 → 单张参考图编辑 | 只调整光影和融合的可控性；模型可能改变花材，须保留原始摆放参考图 |

当前 CloudBase 文档列出文生图模型 HY-Image-3.0-Plus-4090-Tob-v1.0，以及最多一张 PNG/JPEG 参考图（不超过 10 MB）的模型 HY-Image-v3.0-I2I-ToB-v1.0.1。图片理解示例使用 `hunyuan-custom` provider 与 `hunyuan-vision` 模型，并要求在云端配置 BaseURL 与 API Key；是否由用户的活动资源包覆盖仍需账号验证。模型名通过环境配置和能力开关管理，不进入页面业务代码。

场景编辑先保证本地摆放与导出可用。如果用户上传的是带背景花束照片，需额外接入并验证抠图能力；普通图生图不等于主体分割。花束自身的素材画布可以直接导出透明图，真实效果图是否可获得透明主体须单独评估。

生图耗时与小程序前台请求解耦：创建任务写入数据库 → 服务端可靠调度领取任务 → 调用模型 → 转存图片 → 标记结果 → 小程序查询状态。不能在云函数返回后继续依赖未等待的 Promise 执行。异步触发机制须在 P0 确认环境支持；不支持时采用持久任务表与定时调度，不伪造即时进度。

任务使用 queued/running/succeeded/failed 状态，记录 stage、attempt、leaseUntil、providerRequestId。按用户身份、作品版本与请求幂等键去重；并发槽由服务端控制。调用超时但计费状态未知时先核查，不无条件重新生成。任务结束不能覆盖用户已编辑的新版本。

额度在服务端维护预占与结算记录，并与供应商账单核对；不把本地统计当作剩余免费额度的唯一真相。活动额度不等于存储、流量、云函数和其他模型全部免费。生成的短期 URL 应及时转存，作品持久保存 fileID。

## 4. 领域数据与接口

- FlowerDefinition：稳定 flowerId、名称/别名、类别、颜色变体、缩略图、画布素材、单位、采购包装规则及规则版本。
- BouquetDesign：designId、owner、revision、来源、标题、flowerInstances、wrapping、ribbon、decorations、referenceAssetIds、更新时间。
- FlowerInstance：instanceId、flowerId、colorVariant、归一化坐标 x/y、scale、rotation、zIndex。数量由实例汇总，避免实例与 BOM 各自维护而漂移。
- BOM：从指定版本的设计派生；花材按品种与颜色聚合，区分设计用量与采购包装。图片识别初始估算保留识别来源、需确认标记和用户确认值。
- Asset：fileID、owner、用途、尺寸、生成来源、关联作品、到期/清理策略。原始空间照片默认私有。
- GenerationTask：taskId、owner、designId、designRevision、输入摘要、模型、参数、状态、结果、错误、供应商请求号。
- UsageLedger：任务幂等键、额度预占、实际使用、核对状态。去重与任务绑定。

云函数业务操作：getCatalog、saveDesign(expectedRevision)、listDesigns、getDesign、deleteDesign、createTask、getTask、listTasks。用户身份取自服务端可信上下文，不接受客户端传入的 owner 作为授权依据。客户端传 fileID，服务端确认归属后换取供模型读取的受限地址，不接受任意外部 URL。

AI 输出经过服务端结构校验与目录校验；失败时返回可修正的候选或可重试错误。生成图只作为效果参考，不自动反推或覆盖用户确认的 BOM。分享图片与 BOM 均携带同一作品 revision，防止图文错配。

## 5. 新视觉方向：当代花艺画册

品牌统一使用小写 flower。暖白纸面、深墨色文字、苔绿作为主要操作色，花卉照片提供局部色彩。通过留白、清晰字级、非对称图片裁切建立艺术感。减少装饰卡片、渐变、重阴影和无意义英文标签。

| 元素 | 设计规格 |
| --- | --- |
| 色彩 | 纸白 #F6F3ED；正文 #262B27；次级文字 #656C64；苔绿 #425648；分隔 #DCDDD4 |
| 字体 | 品牌与少数标题使用衬线；正文和操作使用系统无衬线；不以极细字重表现高级感 |
| 字级 | 以 375px 宽度设计：标题约 28–34px，正文 15–16px，辅助文字至少 12px，按钮约 16px |
| 间距 | 页面边距 24px；基本间距 4/8/12/16/24/32；内容留白随层级变化 |
| 控件 | 按钮约 48px 高，轻圆角 4–8px；有效点击范围至少约 44px；图标配中文标签 |
| 动效 | 180–240ms 的抽屉与状态过渡；不使用持续晃动、粒子和自动轮播 |
| 图片 | 同一背景、光向和比例的花材照片；透明花材按统一锚点与真实比例归一化 |

首版使用固定视口：顶部品牌、主花束画布、中部操作面板和底部“搭配 / 灵感 / 复刻 / 试花 / 作品”导航。同一页面状态切换入口，不纵向滚动。作品入口分页显示本机保存的花束。

### 页面设计

1. 首页：上方 flower 与微信胶囊安全区域；简短中文标题；一张有呼吸感的花艺主视觉；主要按钮“开始搭配”；下方三个轻量文字入口承接照片灵感、花束复刻、场景试花。
2. 搭配页：主要视区为画布。底部为可展开花材抽屉，分类可直接切换；逐步引导不强制用户线性操作。选中单枝才显示变换工具；撤销、清单与完成入口稳定可达。选材抽屉和 BOM 共用底部空间，不叠加遮挡画布。
3. 包装页/抽屉：包装与丝带用真实小样，保持花束实时可见；确认即回到搭配。
4. 灵感与复刻：大面积上传位；识别后先展示颜色/花材候选供确认，再进入编辑。未知品种以“待确认”展示，不编造精确结果。
5. 结果页：大图、可编辑名称、颜色信息、花材清单；“搭配预览”和“AI 效果参考”清晰区分。生成真实图属于用户主动操作，保留返回编辑能力。
6. 场景页：直接带入当前花束，可更换；上传空间后拖动缩放。保存摆放参考与生成融合效果为不同操作，避免用户误以为图片贴合即完成 AI 融合。
7. 花卡：一张作品图、名称、完整花材与辅料信息；长清单自动续页/拆图，所有条目都必须保留。
8. 作品页：按更新时间展示封面、名称、草稿/完成状态；可继续编辑、重命名、删除。生成中的作品显示真实阶段，退出再进入可恢复。

配套 design-preview.html 展示首页、搭配页与结果页的第一版视觉布局。图片复用现有网页素材，仅用于版式验证；不是重新生成的 AI 作品，也不是已经运行的微信小程序。

## 6. 详细排期与验收

以下是单人连续投入的工作量估算，云资源准备与审核等待另计。AI 可用性先验证，避免前端完成后才发现活动模型不支持所需输入。

| 阶段 | 工作量 | 具体任务 | 交付与验收 |
| --- | --- | --- | --- |
| P0 接入与技术验证 | 2–3 工作日 | 核对计划资源与环境绑定；分别试验图片理解、文生图、图生图；确认计费通道、异步任务执行与单图限制；Canvas 透明素材和触摸原型 | 模型能力矩阵、实际请求记录、素材尺寸规则；未开放能力有明确替代与功能开关 |
| P1 视觉与素材系统 | 3–4 工作日 | 首页/编辑器/结果页高保真设计；定导航和抽屉交互；花材素材规范、包装样张；组件样式变量 | 三个核心页面可点击；375px 与窄屏可读；花材素材来源与使用权可追溯 |
| P2 工程与作品模型 | 2–3 工作日 | 页面/分包结构；领域对象；目录数据；store；本地草稿；云函数与所有权规则；开发/生产配置分离 | 新建、退出、恢复同一作品；云端版本冲突可处理；其他用户不能访问私有作品 |
| P3 搭配编辑器 | 5–7 工作日 | 花材实例添加/删除；数量调整；图层和自动构图；触摸命中/拖动/旋转/缩放；撤销重做；包装；BOM 派生 | 画布与 BOM 一致；变换和撤销不丢失；真机连续拖动流畅；总实例限制经真机确定 |
| P4 输出与作品库 | 3–4 工作日 | 同场景高清导出；长 BOM 花卡；相册保存；微信分享卡片；云端作品封面和列表 | 最大支持清单无截断；分享与图片使用同一版本；权限拒绝有恢复入口 |
| P5 真实 AI 与照片流程 | 4–6 工作日 | 视觉识别结构校验；灵感候选；复刻人工确认；构图参考生图；持久任务、幂等、限流、转存、重试及额度记录 | 三条 AI 请求链真实可用；退出重进能恢复；重复提交不会重复创建任务；BOM 不被模型改写 |
| P6 场景试花 | 3–4 工作日 | 当前花束带入；用户照片抠图能力评估/接入；场景摆放；局部融合试验；参考图与融合图保存 | 自有透明花束必能摆放导出；照片抠图及融合达到样例标准才开启 |
| P7 真机与上线准备 | 3–4 工作日 | iOS/Android 真机；弱网、超时、内存和图片限制；首屏/包体优化；异常日志；隐私说明和作品删除；体验版 | 四个入口形成可用流程，主要异常可恢复，体验版可交付；正式提审另行执行 |

合计约 25–35 工作日。阶段门：P0 能力确认 → P1 核心视觉稿 → P3 可搭配版本 → P5 AI 可用版本 → P7 体验版。首个本地核心体验目标约 12–17 工作日，包含接入验证、设计、基础工程与编辑器。

## 7. 关键验证样例

- 花材数从 1 到上限、删除中间实例、切换包装、撤销连续操作：BOM 数量和图层一致。
- 20 张有代表性的花束照片：单色、多品种、遮挡、复杂背景；建立人工标注清单评估品种与可见数量，不虚报准确率。
- 10 个已确认配方：观察生成图的品种、颜色和构图保留；精确枝数以 BOM 为准。
- 10 个空间样例：桌面/窗边/暗光，检查边缘、阴影、空间结构和花束是否改变。
- 双击生成、断网重进、供应商超时、任务租约过期、结果存储失败：不得静默丢失作品或盲目重复计费。
- 长花卡、相册拒绝、字体回退、低内存：清单完整且操作可恢复。

## 8. 开工依赖与下一步

无需云端信息即可推进：设计稿、素材规范、领域模型和本地搭配画布。

真实联调前需要：小程序 AppID、已绑定的 CloudBase 环境 ID、实际资源包名称/模型清单/有效期，以及对应控制台权限。密钥配置在云端，不要求用户把密钥贴入聊天或前端代码。

先完成 P0 的最小能力验证与 P1 的三个核心页面，再依据样例确定正式花材资产和 AI 提示词。产品字体及素材授权、微信提审要求在实际发布阶段按平台当前规则核对。

## 9. 阶段 1 当前执行记录

按 2026-09-27 的最新要求，当前小程序按两张参考图重建了首页、自定义编辑、识花、识花结果、灵感列表、灵感生花、场景试花、作品预览、材料清单和作品库视图；重复编辑截图合并为一页。自定义页的换色位于右侧小色点，画布支持拖动、缩放、旋转、删除、撤销/重做、包装、BOM 和 PNG 导出。

灵感配色仍保留本地页面数据；生花、识花和场景流程的主链路已经切换到 CloudBase 持久任务，但 `AI_RESOURCES_ENABLED` 默认关闭，因此当前不会调用模型。用户提供的 CloudBase 环境 ID 已存入本地配置文件；Publishable Key 与自建 API Key 均未写入源码。部署依赖记录在 [cloudbase-setup.md](cloudbase-setup.md)。

49 张花材透明素材与 8 张展示照片均有归档原图和小程序优化版本；作品页使用保存时的 Canvas 花束图片，材料清单与花束状态同步。静态检查通过 TypeScript 语法剥离、WXML 结构、事件绑定、活动路由和资源清单检查。当前机器未发现微信开发者工具，因此尚未完成模拟器截图叠加、真机适配和完整交互验收。

之前的阶段探针源码和文档仍留在工作区，但不在 `app.json` 活动路由和 `cloudbaserc.json` 部署列表中；探针函数入口当前返回 mock，不调用混元。
